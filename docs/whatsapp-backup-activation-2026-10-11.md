# גיבוי WhatsApp — בחירת ספק ב־Pulse

תאריך: 11.10.2026 | מערכת: Pulse / שירת הנבל | מצב: הקוד מוכן לבדיקת חיבור ופרסום; **לא בוצע מעבר ספק חי**

## מה בוצע
- מתאם WasenderAPI על בסיס Session API Key ב־Base44 Secrets: `WASENDER_API_KEY`.
- מתאם Green API נשמר ללא מחיקת סודותיו.
- בחירת ספק ברירת מחדל (Green API / WasenderAPI) תחת הגדרות מערכת > הגדרות כלליות > הגדרות ספק WhatsApp. רק בעל המערכת (אותה הרשאה שכבר הייתה למסך הגדרות מערכת) יכול לשנות דרך ה־endpoint.
- בחירת הספק נשמרת ב־AppSettings, `setting_key=whatsapp_default_provider`, ונקראת בצד השרת בכל מסלולי השליחה המרכזיים. ללא רשומה קיימת נשמרת תאימות לבחירה שהייתה דרך `WHATSAPP_ACTIVE_PROVIDER`, שבברירת מחדל היא Green API.
- בכל invocation נתון קוראים את ההגדרה רק פעם אחת בזכות cache מבוסס מזהה client; אין cache בין בקשות ולכן שינוי חדש חל על בקשות חדשות.
- בדיקת חיבור ל־WasenderAPI דרך `GET /api/status`, בלי לשלוח הודעת אמת; אי אפשר לבחור אותו אם מפתח חסר או אם הסשן לא `connected`.
- חיבור מסלולי WhatsApp משיבוצים, התראות, מסמכים, תשלומים והסכמי אירוע לבחירה המשותפת. אין יותר קריאות ישירות ל־Green API מתוך `base44/functions`.
- כשהתוצאה של שליחה מתוזמנת לא ידועה (timeout / שגיאת 5xx), מסמנים `whatsapp_delivery_state=unknown` במידע המתוזמן ומונעים retry אוטומטי של אותה הודעה. שגיאות דחייה חד־משמעיות עדיין מטופלות בנתיב הקיים.
- לא נוספה אוטומציה מתוזמנת ולא נוספו סודות לקוד או ל־GitHub.

## בדיקות שבוצעו
- 26 בדיקות ייעודיות לניהול ספקי WhatsApp, אימות, הודעות, קבצים, מעבר וחזרה (כולן עברו).
- `npm run build`, ESLint לקבצי הממשק ששונו, `deno check` לשכבת בחירת הספק, ובדיקת syntax לפונקציות השרת הקריטיות — עברו.
- בדיקות רגרסיה: 117/118 עברו. כישלון אחד בבדיקת `EventAgreement` על RLS create ישן. קובץ הסכמה לא השתנה ביחס לנקודת השחזור; לא טופל כאן כדי לא לחרוג מהמשימה.

## נדרש להפעלה אמיתית
1. בעל המערכת מזין ב־Base44 Secrets את Session API Key של WasenderAPI תחת `WASENDER_API_KEY`. לא להעביר מפתחות בצ'אט, בצילומי מסך או בקוד.
2. סריקת QR בסשן של WasenderAPI וחיבור `connected`.
3. פרסום האפליקציה בצורה מבוקרת לאחר שהפונקציות וה־UI סונכרנו.
4. במסך הגדרות מערכת: **בדוק חיבור** (קריאה בלבד), וידוא `connected`; בחר WasenderAPI > **שמור ספק ברירת מחדל**.
5. שלח הודעת בדיקה למספר אישי, ואז קישור או PDF. בדוק קבלה בפועל, לא רק `msgId`/HTTP 200.
6. במעבר חזרה ל־Green API, בחר אותו באותו מסך ושמור. החלפת ספק לא שולחת מחדש הודעות ישנות.

## סיכונים ומגבלות
- שליחת ניסיון WasenderAPI מוגבלת לפי תנאי החשבון (לרבות קצב ושליחות ביום). אין לשלוח אצוות גדולות בתקופת ניסיון בלי בדיקת המכסה.
- כשל נתונים או בחירת ספק לא נתמך גורמים למניעת השליחה, בלי fallback אוטומטי שעלול ליצור כפילות.
- אמינות delivery/webhooks לא אומתה מול מפתח אמיתי (טרם הוזן בסביבת ההרצה הזמינה כאן).
- השלמה מקיפה של כפתורי `שלח ידנית` לאחר כשל למסמכים ולשיבוצים הייתה בקשה נפרדת קודמת, ולא נבדקה במקטע זה. לא לסמן אותה כהושלמה עד לבדיקת UI מקצה לקצה.
- המנגנון הקיים של fan-out לתזכורות עדיין יכול לדרוש idempotency נוסף במקרה של קריסת תהליך באמצע שליחת אצווה; לא בוצע שכתוב רחב במסגרת תיקון חירום זה.
- הסוד אינו חשוף לסביבת Sandbox shell ולכן בדיקת נוכחותו דרכה אינה אמינה; צריך לבדוק דרך endpoint מנהל בסביבת הריצה.
